# Канон путей и типов 1С для MCP-инструментов onecdev

Документ — единый и обязательный справочник правил именования путей метаданных
и типов 1С, которые принимают и возвращают MCP-инструменты расширения
`onecdev`. Целевая аудитория — ИИ-агенты, подключённые к локальному
MCP-серверу расширения, и разработчики этих агентов.

Канон один: только русские формы, без английских алиасов, без legacy-форм
7.7/8.0, с предсказуемой структурой. Любой инструмент, который сейчас принимает
аргумент `path`, ожидает строку строго в этом формате. Любой инструмент,
который возвращает путь к узлу, выдаёт его в том же формате.

Документ соответствует главам 1-2 плана `../MCP_REFACTORING_PLAN.md` и
является обязательным дополнением к разделу «MCP-инструменты модификации
конфигурации» в `../AGENTS.md`.

## 1. Главные правила

### 1.1. Множественное число для корней-коллекций

Корневой сегмент пути для коллекций метаданных — всегда множественное число:
`Справочники`, `Документы`, `РегистрыСведений`, `Перечисления`, `Отчеты`,
`Обработки`, `Роли`. Единственное число (`Справочник.Контрагенты`) — это форма
ссылки в запросах 1С, а не путь метаданных, и MCP такие пути отвергает.

### 1.2. Единственное число для подсистем и псевдо-корней

Подсистемы — единственное число: `Подсистема.Продажи`. Псевдо-корни, у которых
по определению ровно один экземпляр в конфигурации, тоже единственного числа:
`Конфигурация`, `Расширение`.

### 1.3. CamelCase без пробелов

Все сегменты — CamelCase без пробелов, дефисов и подчёркиваний:
`КурсыВалют`, не `курсы валют`, не `КУРСЫ_ВАЛЮТ`. Имена объектов на диске
обычно уже соответствуют этому правилу, потому что 1С EDT не пускает пробелы
в именах метаданных.

### 1.4. Точка — единственный разделитель сегментов

Разделитель сегментов — точка. Точка внутри имени сегмента запрещена:
платформа 1С это правило соблюдает на уровне валидатора имён метаданных,
поэтому резолвер инструментария считает любую точку признаком разделителя.

### 1.5. Реквизиты и табличные части — прямые сегменты

Реквизит и табличная часть присоединяются к корневому объекту напрямую,
без сегмента-роли: `Справочники.Контрагенты.ИНН` (реквизит),
`Справочники.Контрагенты.КонтактныеЛица` (табличная часть). Имена в этих
двух категориях уникальны внутри объекта по правилам платформы — конфликт
разрешения невозможен.

### 1.6. Внутри табличной части сегменты возвращаются

Стоит спуститься на уровень ниже — внутрь табличной части — и сегменты
возвращаются. Колонки идут как реквизиты табличной части:
`Справочники.Контрагенты.ТабличнаяЧасть.КонтактныеЛица.Реквизит.ФИО`.
Это нужно, потому что внутри ТЧ могут быть как реквизиты, так и стандартные
реквизиты с одинаковыми именами.

Тот же контейнерный паттерн — второй прецедент у HTTP-сервисов: `URLTemplate`
(URL-шаблон) — контейнер для `Method` (метод), и путь возвращает сегмент
`Метод` так же, как ТЧ возвращает `Реквизит`:
`HTTPСервисы.X.URLШаблон.T.Метод.M`. В отличие от ТЧ, сам `URLШаблон` —
не прямой сегмент (см. §2.4): `HTTPСервисы.X` не содержит других
одноимённых по возможности коллекций, но URL-шаблон синтаксически
рассматривается как отдельный тип метаданных (`MetaKind`), а не роль внутри
`HTTPService`, поэтому его путь всегда идёт через сегмент `URLШаблон`,
без прямой формы.

### 1.7. Подсистемы — без удвоения сегмента

Иерархия подсистем строится без повтора корневого сегмента:
`Подсистема.Продажи.Розница.Возвраты`, а не
`Подсистема.Продажи.Подсистема.Розница.Подсистема.Возвраты`. Префикс
`Подсистема` присутствует только один раз — в самом начале пути.

### 2.2. Псевдо-корни — один экземпляр

| Путь | Что это |
|---|---|
| `Конфигурация` | Узел корня основной конфигурации, для свойств уровня конфигурации. |
| `Расширение` | Узел корня расширения. |

Псевдо-корни используются как путь для `onecdev_configuration_info`,
`onecdev_validate_configuration`, `onecdev_get_properties`,
`onecdev_set_property_by_path` и `parentPath` в `onecdev_compile_subsystem`
и `onecdev_compile_role`.

#### Формы: тело и дескриптор

Формо-инструменты (`form_info`, `validate_form`, `compile_form`, `edit_form`) работают с **телом**
формы — `Ext/Form.xml`. Дескриптор формы (`<Имя>.xml`, служебные свойства и ссылка на модуль) им не
нужен. Резолвер `resolveFormXmlByCanonical` (`ui/mcp/McpPathResolvers.ts`) возвращает именно тело:

| Канонический путь | Тело формы (`Ext/Form.xml`) | Дескриптор |
|---|---|---|
| `Справочники.X.Форма.Y` | `Catalogs/X/Forms/Y/Ext/Form.xml` | `Catalogs/X/Forms/Y.xml` |
| `ОбщиеФормы.X` | `CommonForms/X/Ext/Form.xml` | `CommonForms/X.xml` |

Прежний JSDoc резолвера обещал дескриптор, а фактически отдавался `node.xmlPath` — контракт не держался,
поэтому он **сменён на тело** и закреплён тестами.

**Почему нельзя взять `node.xmlPath`.** У узла формы объекта `xmlPath` — это XML **объекта-владельца**
(`Catalogs/X.xml`), а не путь формы; подробнее — в
[metadata-navigator.md](./metadata-navigator.md#инвариант-узла-формы-xmlpath-принадлежит-владельцу).
Арифметика адреса формы живёт в `MetaPathResolver` (`resolveFormXmlByDescriptor`,
`resolveChildFormDescriptor`, `resolveChildFormXml`) и подаётся потребителям через единый адаптер
`ui/tree/formNodePaths.ts` (`resolveObjectFormNodeParts`, `resolveFormBodyFromNode`). Тело выводится
явно (`dirname` + `basename` + `Ext/Form.xml`), а не через `getObjectLocationFromXml`: та эвристика
глубокой/плоской раскладки сверяет имя файла с именем родительского каталога и на форме с именем
`Forms` (`Forms/Forms.xml`) уводит путь на уровень выше.

**Guard по содержимому.** Даже при верном пути инструмент не пишет форму поверх чужого XML:
`FormShared.readFormXml`/`assertFormRootXml` проверяют, что первый элемент документа (после BOM, пролога и
комментариев) — `Form`. `edit`/`info`/`compile` при несовпадении бросают ошибку (для XML объекта
метаданных — с подсказкой про `Forms/<Имя>/Ext/Form.xml`), `validate_form` возвращает отчёт с ошибкой
(read-only инструмент отвечает отчётом, а не исключением). Проверять надо **корень документа, а не
вхождение тега**: в XML справочника есть `<Form>ФормаСписка</Form>` внутри `<ChildObjects>`, и проверка
подстрокой `<Form` принимала его за форму. `resolveFormXmlPath` при этом бросает на любом существующем
файле, который не `Form.xml` и рядом с которым нет тела (раньше возвращал сам входной файл).

**Вердикт `validate_form`: ошибки и предупреждения.** Отчёт содержит оба счётчика (`errors`,
`warnings`), и они разные по смыслу: ошибка — то, чего в корректной выгрузке платформы не бывает вообще;
предупреждение — подозрительное, но платформа такое выгружает штатно (команда без `<Action>`,
`AutoCommandBar` с `id` не `-1`, неизвестная/отсутствующая `version`). Поэтому агент не должен считать
форму битой из-за одних предупреждений, а вызывающий код — сводить вердикт только к `errors === 0` и
игнорировать `warnings` в отчёте пользователю. Полная классификация, числа эталона и критерий «выгрузка
платформы проходит чисто» —
[xml-format-rulesets.md](./xml-format-rulesets.md#formvalidateservice-платформенная-выгрузка-обязана-проходить-чисто).

## 3. Канон типов значений 1С

Раздел соответствует главе 2 плана. Реестр типов выдаётся инструментом
`onecdev_list_supported_types` (платформенные типы) и
`onecdev_list_available_types` (с учётом конфигурации и контекста свойства).
Имена, передаваемые в `onecdev_set_type`, — только русские из этого
реестра.

### 3.1. Базовые платформенные типы (новинка: ключевая часть E2)

Базовый реестр платформенных типов теперь живёт в `infra/xml/PlatformTypeRegistry.ts`
и читает данные из `domain/CanonicalNames.ts`. Это ключевая новинка
рефакторинга MCP — раньше эти типы были захардкожены в нескольких местах.
В частности, добавлена поддержка `УникальныйИдентификатор` (XML-токен `v8:UUID`)
как полноценного платформенного типа реквизитов прикладных объектов
и форм.

| Канон (рус) | XML | Контекст |
|---|---|---|
| Строка | String | оба |
| Число | Number | оба |
| Булево | Boolean | оба |
| Дата | Date | оба |
| ДатаВремя | DateTime | оба |
| ХранилищеЗначения | ValueStorage | оба |
| УникальныйИдентификатор | UUID | оба |
| ДвоичныеДанные | BinaryData | оба |
| Картинка | Picture | оба |
| Тип | Type | реквизит формы |
| ОписаниеТипов | TypeDescription | реквизит формы |
| СписокЗначений | ValueList | только формы |
| ТаблицаЗначений | ValueTable | только формы |
| ДеревоЗначений | ValueTree | только формы |
| Массив | Array | только формы |
| ФиксированныйМассив | FixedArray | только формы |
| Структура | Structure | только формы |
| ФиксированнаяСтруктура | FixedStructure | только формы |
| ТабличныйДокумент | SpreadsheetDocument | только формы |
| ФорматированнаяСтрока | FormattedString | только формы |

Контекст:
- «оба» — допустим как тип реквизита прикладного объекта и как тип реквизита формы.
- «только формы» — нельзя как тип реквизита метаданных, только в форме.

### 3.2. Производные ссылочные типы — генерируются по конфигурации

Производные типы генерируются по фактическому составу выбранной конфигурации.
Чтобы получить их, инструмент должен видеть конфигурацию (передан `configuration`,
либо в workspace единственная конфигурация).

| Корневой тип метаданных | Производные (русский ↔ XML) |

| Справочник | СправочникСсылка ↔ CatalogRef, СправочникОбъект ↔ CatalogObject, СправочникМенеджер ↔ CatalogManager, СправочникВыборка ↔ CatalogSelection, СправочникСписок ↔ CatalogList |

| ПланВидовРасчета | ПланВидовРасчетаСсылка/Объект/Менеджер ↔ ChartOfCalculationTypesRef/Object/Manager |

| РегистрСведений | РегистрСведенийНаборЗаписей ↔ InformationRegisterRecordSet, РегистрСведенийКлючЗаписи ↔ …RecordKey, РегистрСведенийМенеджерЗаписи ↔ …RecordManager, РегистрСведенийВыборка ↔ …Selection, РегистрСведенийСписок ↔ …List, РегистрСведенийМенеджер ↔ …Manager |
| РегистрНакопления | те же 6 (Accumulation…) |
| РегистрБухгалтерии | те же 6 (Accounting…) |
| РегистрРасчета | те же 6 (Calculation…) + РегистрРасчетаПерерасчет ↔ CalculationRegisterRecalculation |
| Константа | КонстантаМенеджер ↔ ConstantManager, КонстантаМенеджерЗначения ↔ ConstantValueManager |

Запись в XML: ссылочный тип пишется как `<v8:Type>cfg:CatalogRef.X</v8:Type>` (см.
[xml-format-rulesets.md](./xml-format-rulesets.md#префикс-ссылочного-типа-cfg-в-xml-объекта-метаданных)).
Значение на входе `set_type` можно передавать в форме, в которой оно записано в выгрузке
(`cfg:CatalogRef.Товары`, `d5p1:CatalogRef.Товары`) — неймспейс-префикс при сравнении снимается.

**Контракт (не дефект): в расширении `set_type` допускает ссылки только на собственные и заимствованные
объекты.** Ссылка на объект основной конфигурации, не заимствованный в CFE, отбивается — сначала
`onecdev_cfe_borrow`. Основание — эталон `example/2.21/src/cfe/EVOLC`: все объекты основной
конфигурации, на которые есть ссылки, присутствуют там как заимствованные заглушки, контрпримеров нет.
Закреплено тестом «запрещает ссылочный тип CFE, если объект не заимствован в расширение»
(`mcpPropertyService.test.ts`).

Фильтрация по контексту свойства:

- **Тип реквизита прикладного объекта** (`metadataAttribute`) — примитивы из §3.1
  с пометкой «оба» + только `*Ссылка` и `ОпределяемыйТип` из §3.2.
- **Тип реквизита формы** (`formAttribute`) — всё из §3.1 + всё из §3.2 + `DynamicList`.
- **Источник подписки на событие** (`eventSource`) — только `*Объект`, `*НаборЗаписей`,
  `КонстантаМенеджерЗначения`.
- **Тип параметра команды** (`commandParameter`) — только `*Ссылка` и `ОпределяемыйТип`.

### 3.3. Квалификаторы типов

Квалификаторы передаются в `onecdev_set_type` как отдельные поля
(`length`, `digits`, `fractionDigits`, `dateFractions`, `allowedSign`,

| Канон (рус) | XML | Где |
|---|---|---|
| Длина | length | Строка |

## 4. Запреты — что MCP отвергает

MCP-инструменты принимают только канон. Любая попытка передать одну из форм
ниже завершается ошибкой резолвера с сообщением «используй канон».

### 4.1. Английские формы

- `Catalog.X`, `Catalogs.X` — английские имена корней не принимаются ни в одном
  числе. Используй `Справочники.X`.
- `Document.X`, `Documents.X` — то же. Используй `Документы.X`.
- `InformationRegister.X`, `InformationRegisters.X` — используй `РегистрыСведений.X`.
- Внутренние сегменты тоже только русские: `Form.Y` → `Форма.Y`,
  `Command.Z` → `Команда.Z`, `Template.X` → `Макет.X`, `ObjectModule` → `МодульОбъекта`.

### 4.2. Единственное число для коллекций

- `Справочник.Контрагенты` — это форма запроса 1С, а не путь метаданных.
  В MCP — только `Справочники.Контрагенты`.
- `Документ.РасходТовара` → `Документы.РасходТовара`.
- `РегистрСведений.КурсыВалют` → `РегистрыСведений.КурсыВалют`.

Исключение — те самые корни, у которых единственное число каноническое:
`Подсистема`, `Конфигурация`, `Расширение`.

### 4.3. Грязные сегменты

- `Справочники.X.Реквизиты.Y` — лишний сегмент-роль `Реквизиты` (мн.ч.).
  Реквизит присоединяется прямо: `Справочники.X.Y`.
- `Справочники.X.ТабличныеЧасти.T` — лишний сегмент `ТабличныеЧасти` (мн.ч.).
  Используй прямую форму: `Справочники.X.T`.
- `Справочники.X.Формы.Y` — мн.ч. вместо канонического `Форма` (ед.ч.).
  Используй `Справочники.X.Форма.Y`.
- `Справочники.X.Команды.Z` → `Справочники.X.Команда.Z`.

Соответствующие сегментированные роли пишутся в единственном числе: `Форма`,
`Команда`, `Макет`, `СтандартныйРеквизит`, `Реквизит` (только внутри ТЧ),
`РеквизитАдресации`, `ПризнакУчета`, `ПризнакУчетаСубконто`, `Перерасчет`.

### 4.4. Удвоение префикса у подсистем

- `Подсистема.А.Подсистема.Б.Подсистема.В` — повтор сегмента `Подсистема`
  для каждого уровня иерархии. Канон — единичный префикс:
  `Подсистема.А.Б.В`.

### 4.5. Точка внутри имени

Имя объекта 1С не содержит точку — это запрещено платформой. MCP-резолвер
любую точку трактует как разделитель сегментов. Это уберегает агентов от
двусмысленных путей, которые пришлось бы парсить «как платформа».

## 5. Как использовать с MCP-инструментами

### 5.1. Общий аргумент `path`

После рефакторинга E5 у всех инструментов, работающих с одним узлом, аргумент
называется одинаково: `path`. Никаких `objectPath`, `formPath`, `templatePath`,
`rightsPath`, `subsystemPath`, `ciPath` и `modulePath` больше нет. Если
инструмент работает с несколькими путями сразу (`onecdev_validate_metadata`),
он принимает массив через `paths`.

Парные инструменты, создающие новый объект внутри родителя
(`onecdev_compile_subsystem`, `onecdev_compile_role`,
`onecdev_add_form`), принимают `parentPath` — канонический путь
родителя (`Конфигурация`, `Расширение`, `Подсистема.X.Y` или корневой
объект).

### 5.2. `onecdev_tree` для обзора

Перед любой массовой работой с конфигурацией удобно один раз получить плоский
список канонических путей через `onecdev_tree`:

```json
{
  "configuration": "cf",
  "scope": "objects",
  "depth": "objects",
  "include": ["Справочники", "Документы"],
  "limit": 5000
}
```

`tree` возвращает плоский массив строк, без свойств — за свойствами идти
прицельно через `metadata_info`. Это снимает необходимость в пагинации `list`
на больших конфигурациях.

Допустимые значения:
- `scope`: `all` | `objects` | `common` | `subsystems`.
- `depth`: `roots` (только корни), `objects` (корни + объекты), `children`
  (корни + объекты + дочерние элементы первого уровня).

### 5.3. `onecdev_resolve_path` для отладки

Если непонятно, как выглядит канон для конкретного объекта в работе агента, —
передай сомнительный вход в `onecdev_resolve_path` и посмотри `canonical`.
Инструмент нормализует путь и проверяет существование узла:

```json
{ "path": "Справочники.Контрагенты", "configuration": "cf" }
```

Результат:

```json
{
  "canonical": "Справочники.Контрагенты",
  "exists": true,
  "nodeKind": "Catalog",
  "xmlPath": "…/Catalogs/Контрагенты.xml"
}
```

Если узла нет — `exists: false` без ошибки. Если форма не канон — ошибка с
подсказкой канона.

### 5.4. `onecdev_list_supported_types` для выбора типа

Полезен перед `onecdev_set_type`, особенно когда конфигурация большая и
агент не знает, какие справочники там есть.

```json
{ "context": "metadataAttribute", "configuration": "cf" }
```

Возвращает группы примитивов и ссылочных типов, отфильтрованные по контексту.
Базовая группа выдаётся даже без `configuration`; ссылочные группы появляются
только при выбранной конфигурации.

### 6.2. Инструменты обмена CF/CFE через пакетный Конфигуратор

У `onecdev_dump_cf` и `onecdev_load_cf` нет аргумента `path` в каноне,
хотя сама конфигурация/расширение узлом дерева являются, — потому что предмет
операции здесь не узел, а файл на диске (куда выгрузить/откуда загрузить
бинарник). `extensionName` — опциональное имя расширения (пусто = основная
конфигурация), а не канонический путь; `outputFile`/`inputFile` — обычные
файловые пути, аналогично `objectPath`/`outputDir` у `create_epf`/`cfe_diff`
ниже.

Основная и подробная эмпирика поведения платформы (в частности, почему у
обоих инструментов НЕТ параметра `allExtensions` ни в каком виде) —
[architecture.md](./architecture.md#паттерн-бинарный-обмен-cfcfe-через-пакетный-конфигуратор-dumpcfgloadcfg).

| Инструмент | Аргументы | `destructiveHint` | Особенности |
|---|---|---|---|
| `onecdev_dump_cf` | `outputFile` (FS), `extensionName?`, `overwrite?` | `false` | Пустой/отсутствующий `extensionName` — основная конфигурация; непустой — расширение (суффикс файла обязан совпасть: `.cf`/`.cfe`). Файл на целевом пути появляется только при успехе (staging-схема). |
| `onecdev_load_cf` | `inputFile` (FS), `extensionName?`, `confirm` (обязательный), `applyToDatabase?` | `true` | `confirm: true` обязателен — операция необратима. `extensionName`, которого ещё нет в базе, создаёт новое расширение. Без `applyToDatabase: true` конфигурация базы НЕ обновляется; ответ инструмента содержит `projectSourcesOutdated: true` — сигнал агенту, что XML-выгрузка проекта рассинхронизирована с базой и нужен импорт. |

Оба инструмента запрещают `-AllExtensions` на уровне схемы входа (поля просто
нет) и берут тот же общий замок операций над конфигурацией, что импорт/
обновление базы — конкурентный вызов от агента и от пользователя одновременно
получит явную ошибку «операция уже выполняется», а не повреждённые данные.

Пакетные инструменты (все расширения базы; механизм, политики отказа и
причины решений — «Пакетный случай» в [architecture.md](./architecture.md#пакетный-случай-все-расширения-базы-одной-операцией-dump-cfe-allload-cfe-all)):

| Инструмент | Аргументы | `destructiveHint` | Особенности |
|---|---|---|---|
| `onecdev_dump_all_cfe` | `outputDir` (FS), `overwrite?` | `false` | Список расширений берётся у базы (цикл по `/DumpDBCfgList -AllExtensions`, а не ключ `/DumpCfg`). Ответ: `dumped[]`, `failed[]`, `manifestFile`. Частичный отказ — УСПЕХ со списком `failed` (базу выгрузка не меняет, остальные бэкапы ценны). Без `overwrite` существующие файлы плана — отказ до старта. |
| `onecdev_load_all_cfe` | `inputDir` (FS), `confirm` (обязательный), `createMissing?`, `applyToDatabase?` | `true` | `confirm: true` обязателен. При сбое на любом расширении загрузка ОСТАНАВЛИВАЕТСЯ и инструмент бросает исключение: сбойное расширение в состоянии `stateUncertain`, следующие не трогались. Ответ при успехе: `loaded[]`, `applied[]`, `notInDirectory`, `ignoredFiles`, `restoredByFileName` (расширения, имя которых взято из имени файла, а не из манифеста — признак возможного чужого поколения бэкапа), `projectSourcesOutdated: true`. `applyToDatabase` — `/UpdateDBCfg -Extension` по одному на каждое загруженное расширение. |

### 6.5. Инструмент истории хранилища

`onecdev_repository_history` (`ui/mcp/registration/McpRepositoryTools.ts`) — только чтение: изменённых
файлов нет, ни проверок блокировки, ни аренды guard. Пользовательская сторона и сервис —
[repository-file-sync.md](./repository-file-sync.md#история-хранилища).

| Аргумент | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `path` | канон | — | `Конфигурация`/`Расширение` — вся история; `Справочники.X`, `Справочники.X.Форма.Y`, `Справочники.X.Макет.Y`, `ОбщиеФормы.X`, `Подсистема.A.B` — история этого объекта (с подчинёнными) |
| `configuration` | строка | — | выбор конфигурации/расширения при нескольких |
| `limit` | 1..100 | 20 | размер страницы |
| `beforeVersion` | целое ≥ 2 | — | курсор: вернуть версии строго ниже этого номера |
| `maxChangesPerVersion` | 0..1000 | 100 | сколько изменений показать на версию; остаток — `changesTruncated: true` |

- Реквизит, ТЧ и другие дочерние элементы — отказ с подсказкой пути объекта-владельца: история хранится по
  единице хранилища (объект, форма, макет), а не по их частям.
- Листание: ответ содержит `nextBeforeVersion` (= старший непоказанный номер + 1), пока есть более ранние версии;
  следующий вызов — с `beforeVersion = nextBeforeVersion`. `total` — показано плюс осталось.
- Ответ: `target`, `object?` (`objectId`, `title`), `total`, `versions[]` (`number`, `author`, `date`, `comment`,
  `label?`, `configVersion`, `changes[]` — `objectId`/`title`/`kind`, `changesTruncated`), `nextBeforeVersion?`.
  Без uuid версий и авторов, без версии платформы и без хешей.
- Не подключено / файловое хранилище (`.1CD`, отсылка к «Построить отчет по хранилищу») / отказ сервера — ошибка
  инструмента без секретов. Английские и legacy-формы пути отбиваются каноном.

### 6.6. Неинтерактивный выбор целей в `onecdev_execute_command`

Для `importConfigurations` и `updateChangedConfigurations` (`ui/mcp/registration/McpConfigLifecycleTools.ts`):

| Аргумент | Тип | Смысл |
|---|---|---|
| `configurations` | `string[]` | имена из `onecdev_workspace_overview` или из `available` прошлого ответа; без учёта регистра, `ё` ≠ `е` |
| `all` | boolean | все кандидаты; для `updateChangedConfigurations` — только изменённые |

- `configurations` и `all` взаимоисключающие; для `refresh` недопустимы. Нарушение — `isError` инструмента.
- Без обоих аргументов: единственный кандидат выполняется сразу, иначе исход `invalid-selection` с
  `reason: 'selection-required'`, `available` (имена кандидатов) и `message`.
- Неизвестное имя — `invalid-selection` с `reason: 'unknown-names'`, `unknown` и `available`; частичного
  выполнения нет (ни одна из названных конфигураций не обрабатывается).
- Разделение ошибок: ошибка формы входа (несовместимые аргументы, недопустимые для команды) — `isError`;
  ошибка по данным (не тот выбор при текущем составе конфигураций) — обычный исход команды
  `invalid-selection`, чтобы агент поправил вызов по `available` без повторного обзора.
- Окно выбора из MCP не открывается, поэтому исход `cancelled` недостижим; всего исходов 7
  (`done`/`no-changes`/`no-targets`/`cancelled`/`busy`/`failed`/`invalid-selection`).

## 7. Дополнительные замечания

- Если в workspace несколько конфигураций (`cf` + одно или несколько `cfe/*`),
  большинство инструментов требует параметр `configuration`. Сообщение об
  ошибке перечисляет доступные имена.
- Для CFE канон путей тот же — `Справочники.X`, потому что заимствованный
  объект имеет тот же корневой сегмент. Признак «заимствованный» возвращается
  в DTO выдачи (`borrowed: true`).
- Пути в выдаче всегда канонические. Никаких параллельных алиасов в ответе.
- Если в имени объекта по выгрузке оказался пробел (платформа теоретически
  допускает, EDT — обычно нет), резолвер примет такой узел, но в выдаче
  выделит его кавычками: `Справочники."Имя с пробелом"`. Это маркер опасности —
  такой объект лучше переименовать.
- **Отложено (не реализовано):** read-only-инструмент `onecdev_list_database_extensions`
  — список расширений, подключённых к базе проекта (тот же источник, что
  QuickPick команды `onecdev.connectExtension`), для ИИ-агентов, планирующих
  подключение/выгрузку расширения без ручного опроса пользователя. Переиспользует
  готовую связку `ExtensionCommandRunner.listConnectedDatabaseExtensions` → CLI
  `list-db-extensions` → `infra/environment/ExtensionListParser.ts` (см.
  [architecture.md](./architecture.md#паттерн-чтение-данных-из-базы-через-пакетный-конфигуратор-file-handoff)) —
  бизнес-логику писать заново не нужно, только регистрация tool'а в
  `V8McpServer`/доменном модуле `registration/`.
