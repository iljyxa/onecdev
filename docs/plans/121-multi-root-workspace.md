# Несколько папок-проектов в одном окне (#121)

База проектирования — `origin/main` на коммите `18d317a`. Трек LARGE. Меняются время
жизни зависимостей в `Container`, маршрутизация команд и состояние webview. Реализация
разбита на четыре этапа с сохранением рабочего режима одной папки. [Постановка #121](https://github.com/iljyxa/onecdev/issues/121)

Основной объём приходится на извлечение проектного цикла из `Container` и перенос
регистраторов команд на явный контекст. Действующие протоколы хранилища и модели XML
уже работают с известным корнем. Этапы 2 и 3 требуют сверить потребителей `CommandServices`.

## Критерии приёмки

- Две папки с одноимёнными CF, CFE и объектами открываются в одном окне. Навигатор
  показывает выбранный проект и даёт переключиться, в том числе между папками с одинаковым
  отображаемым именем. Выбор сохраняется в состоянии рабочей области. Переключение сохраняет
  фильтры и раскрытие каждого проекта и не требует заново опрашивать хранилище.
- У каждой папки свои `env.json` / `autumn-properties.json`, `ProjectSecretStorage`,
  `RepositoryService` с `RepositoryLockStatusService`, `.onecdev/repository/state.json`,
  снимки, временные файлы, дерево, наблюдатели и вычисляемые статусы. Опрос, захват,
  получение, освобождение и read-only в A применяются к A, даже когда в навигаторе видна B.
- Команда палитры без цели при наличии нескольких доступных проектов предлагает выбрать
  папку, при одной сохраняет прежний сценарий. Отмена выбора исключает побочные эффекты.
  Команда от узла или документа определяется по ресурсу. Действия панели без узла
  используют проект, показанный в момент создания действия. Вызов с явной устаревшей
  или чужой целью завершается до обращения к базе и записи файлов.
- Пустая локальная папка доступна для инициализации, папка без подключённого хранилища
  не участвует в фоновом опросе. Рабочая область с произвольной папкой первой продолжает
  показывать следующий проект. У вложенных папок ресурс принадлежит самому глубокому
  открытому корню. Каждый найденный CF/CFE входит максимум в один проект.
- Удаление папки отписывает её наблюдателей, исключает её из выбора и запрещает новые
  операции. Текущая операция сохраняет привязку к исходному экземпляру контекста.
  Повторное добавление той же папки ждёт завершения её предыдущего экземпляра.
  Закрытие окна освобождает оконные и проектные ресурсы.
- В одном проекте сохраняются существующие идентификаторы команд, форматы файлов и ключи
  секретов, схема и пути MCP. В окне с несколькими независимыми папками MCP по-прежнему
  обращается к исходной папке окна. Два окна с одной и той же рабочей областью сохраняют
  существующее поведение блокировок и MCP-конфликтов. Новая блокировка между окнами
  находится за рамками #121.

## Владение ресурсами

| Область | Владелец |
| --- | --- |
| Регистрация команд, webview, схемы `onec-git`, событий редактора и декораций | `Container`, по одной регистрации на окно. |
| `OutputChannel`, `ConfigurationOperationGuard`, статус-бары команд, LSP и BSL Analyzer MCP | `Container`. Guard сохраняет оконную сериализацию. Две папки могут ссылаться на одну базу, поэтому ключом guard не становится путь папки. `onecdev.isUpdatingConfigurations` отражает тот же общий guard. |
| Привязка, секреты, состояние захватов, снимки, история, поддержка, проектное окружение, standalone, агент Конфигуратора и git-кэш | `ProjectContext` для конкретной папки. CLI и агент получают рабочий каталог и секрет из зафиксированного контекста. |
| Локальная модель дерева, поиск, фильтр рабочего набора, сканер изменений, кэши, подавление собственных событий, `ConfigurationCleanWindow`, конфигурационные и файловые наблюдатели | `ProjectContext`. Асинхронные события обновляют модель владельца. Видимые панели обновляются только для выбранного контекста. |
| Панели настроек окружения, standalone, подключения и помещения, редактор подсистемы | Сессия панели привязана к исходному контексту до закрытия. На удаление проекта панель инвалидируется, отложенная отправка формы отклоняется. |
| Дерево, свойства и «Изменения метаданных» | По одному видимому представлению на окно. Источник дерева и изменений меняется при выборе проекта. Свойства сбрасывают выбор и отложенные ответы, затем восстанавливают допустимый узел выбранного проекта. |

`Container.bootstrap()` остаётся единственной точкой сборки. Разделить длинный `Container`
по ответственностям при извлечении проектного цикла, регистрации оконных интеграций и
наблюдателей. Проект создаёт существующие сервисы через фабрику, которую вызывает Container.
Класс проекта получает ресурсы через зависимости. Сервисы без состояния, привязанного к
проекту, можно по-прежнему создать один раз, проверив характер их кэшей и колбэков.

### Папка, путь и конфигурация

- Брать список из `workspace.workspaceFolders` и обновлять по `onDidChangeWorkspaceFolders`.
  Поддерживаемые папки определяет существующая модель локальных путей. Для `file:`
  использовать `uri.fsPath`, прочий URI сохранять вне набора доступных проектов,
  без попытки прочесть его через Node FS. Удалённый extension host с локальными для
  него файловыми путями подчиняется тем же правилам.
- Ключ проекта — сравнимый абсолютный путь через `pathKey`. Имя, индекс папки и текущий
  редактор ключом не являются. Абсолютный путь в конструкторе `ProjectSecretStorage`
  сохранять в исходном виде, иначе сменятся существующие ключи БД. Пароль хранилища
  использует существующий `buildRepositoryScopeKey` с абсолютным путём CF/CFE.
- Сопоставлять пути по сегментам через `path.relative` на нормализованных путях,
  с проверкой диска и границы `..`. Проверка владельца допускает корень и потомков.
  Применить общий предикат границы также в `RepositoryService.findConfigRoot()`, где
  сейчас используется `startsWith(workspaceRoot)`. Результаты discovery и события
  `RelativePattern` проверять тем же правилом. Перед записью через путь из команды
  проверять фактический файловый корень с существующими средствами `WorkspaceWritePath`
  и проверкой владельца целевого или ближайшего существующего родителя. Алиасы двух
  папок на один физический каталог регистрировать один раз, вторую помечать недоступной.
  Разрешать физические пути на этапе регистрации и на границе записи, вне горячего пути
  декораций и дерева.
- `ConfigLocator` по умолчанию работает как сейчас. Вызов из проектного контекста
  отсекает вложенные открытые папки при обходе. Для найденного CF/CFE отдельно проверить,
  что его `rootPath` целиком принадлежит проекту. Если другая открытая папка расположена
  **внутри** самого дерева выгрузки, весь пересекающийся CF/CFE недоступен для операций,
  заменяющих выгрузку целиком и блокировок хранилища. Показать диагностическое сообщение
  с обоими путями и исключить конфликтующий CF/CFE из операционного каталога. При изменении
  топологии пересчитать прежнего и нового владельцев. Дополнительная папка внутри проекта,
  которая не пересекает его выгрузку, сама по себе работе не мешает.
- У каждой папки собственная миграция legacy-каталога перед созданием сервисов и
  собственный `sweepStaleOperationTemp`. Миграцию и первую тяжёлую подготовку хеш-кэшей
  запускать при первом обращении в проект, а фоновый запуск разнести по задачам очереди.
  Фоновый опрос — только после готовности сервиса, только для подключённых целей и с
  существующей проверкой Workspace Trust. Завершение старой подготовки после удаления
  не публикует состояние и не запускает новые опросы.

### Команды, операции и панели

Ввести проектный регистратор поверх `vscode.commands.registerCommand`. Каждый регистратор
команд явно описывает свою цель. Чтение первого позиционного аргумента общим эвристическим
правилом опасно, поскольку bulk-команды передают `request?: unknown`, а у других команд есть
дополнительные опции. Проектная команда получает `CommandServices` один раз до обработчика
и работает с ним до окончания. Глобальные команды AI/LSP регистрируются отдельно в том же
оконном реестре. Идентификаторы команд и публичные позиционные аргументы сохраняются.

| Источник | Выбор |
| --- | --- |
| Действие от узла, явный URI, внутренний запрос с владельцем | Проверить цель всеми доступными идентификаторами. При конфликте, отсутствии владельца или недействительной цели завершить с сообщением. |
| Действие в навигаторе без узла | Использовать проект, зафиксированный в запросе панели. При смене проекта устаревшие сообщения панели игнорируются. |
| Палитра без цели | `showQuickPick` по доступным для команды папкам в порядке рабочей области, при одной выбрать сразу. Показать имя и полный путь, при отмене завершить. Для `repository.refreshLocks` далее обновляются все подключённые CF/CFE выбранной папки. |
| Вложенный вызов из запущенной команды, кнопка уведомления или завершение операции | Использовать сохранённый экземпляр контекста. Сквозной вызов без аргумента должен получить явного владельца или вызвать общий обработчик напрямую. |

Привязка к проекту фиксируется до первого проектного I/O и передаётся в замыкания
диалогов и `afterSuccess`. Вход с удалённой папкой и диалог, подтверждённый после её
удаления, завершаются без запуска платформы. При уже начавшейся мутации не переназначать
контекст и не прерывать произвольно начатую работу. Дать завершиться обязательной записи
состояния и очистке временных файлов в A и подавить фоновые/оконные публикации. Если
папка физически исчезла или изменилась граница владения во время работы, остановить
следующие этапы записи в выгрузку и сообщить исход операции на сервере отдельно от
состояния файлов. Перед каждым новым шагом мутации перепроверять весь набор затрагиваемых
путей по актуальной топологии. Для записи одного файла граница — существующий атомарный
примитив. Для замены или удаления каталога проверка охватывает всё поддерево, включая
новые вложенные корни. Изменение топологии должно стать видимым проверкам до любой
асинхронной подготовки новых контекстов. Повторять проверку после асинхронной подготовки
прямо перед синхронной заменой и перед началом запасного пофайлового пути в
`syncDirectorySnapshot`. Тот же принцип действует на границе рекурсивного удаления
и запуска внешнего процесса, который пишет в проект. Если процесс продолжает работу после
`await`, писать во временный каталог и проверять назначение перед переносом в выгрузку.
После снятия guard действуют прежние правила post-mutation и диалога о конфликте.
Для ожидающих действий использовать существующие точки отмены и очистку в `finally`.

Для дерева и свойств ключ позиции в дереве недостаточен. При смене проекта пересоздать
поколение представления и привязать сообщения с действиями к этому поколению. Узлы и
action payload получаются из host-side карты, ключ проекта из webview служит только для
сверки. Просроченный `executeNodeAction`, выбор и редактирование свойства с совпавшим
`nodeId` из другого проекта должны отсеяться до вызова команды. Протоколы менять с обеих
сторон. Ключ выбора и раскрытия в `workspaceState` привязать к проекту. Старое сохранённое
выделение принять однократно для единственной папки, если оно сопоставляется с её узлом.

Read-only контролировать по владельцу ресурса. Оконная подписка на открытие редактора
получает `RepositoryService`/состояние поддержки нужного проекта. Событие изменения
`lockState` пересчитывает только вкладки его проекта, включая локальную сторону diff.
Глобальный провайдер git-декораций аналогично выбирает готовый кэш владельца. Для удалённой
папки обработать только сеансовое readonly, выставленное расширением, учитывая существующие
правила для dirty и невидимых вкладок. Подписки и очереди, пережившие смену выбранного
проекта, работают со своими замыканиями, включая таймеры из `Container` и наблюдатель Git API.

### Агент Конфигуратора

В многопапочном окне читать `onecdev.configuration.operationMode` и `onecdev.agent.*`
с ресурсом папки. Для одновременной работы агентов нескольких проектов нужны разные
порты SSH. Оконный реестр резервирует порт на время запуска и жизни агента вместе
с экземпляром проекта. Совпадающий порт отклоняется до запуска или подключения,
включая разные написания локального адреса. Сообщение указывает папку-владельца и
предлагает отдельный порт или пакетный режим. Порт освобождается после завершения
промиса запуска, сессий и своего процесса. Проверять фактические параметры `/AgentPort`
и `/AgentListenAddress`, если пользователь передал их в `agentModeArgs`.

Для автозапуска проверять, что порт свободен перед стартом и что слушатель принадлежит
запущенному процессу до SSH-подключения. Открытый TCP-порт сам по себе не подтверждает
готовность своего агента. Если платформа не даёт подтвердить владельца, сообщить об
этом до запуска команды через SSH и оставить для этой папки пакетный режим. При
`autoStart: false` в многопапочном окне требовать явный адрес и порт в настройках
папки. Внешний endpoint резервируется за этой папкой, расширение освобождает только
свои сессии. В однопапочном режиме прежние настройки по умолчанию сохраняются.

### MCP и LSP

- Встроенный `V8McpServer` использует один endpoint и один исходный проект. При первом
  запуске закрепить в `workspaceState` ключ первой папки, как в текущем `activate()`,
  до запуска сервера. Хранить закрепление и при исчезновении папки. Это важно при
  перезапуске extension host после изменения первого корня. Выбор в навигаторе,
  перестановка папок и изменение настроек MCP не меняют привязку. Панель AI
  показывает полный путь закреплённого проекта и причину недоступности, если он
  отсутствует. Схемы инструментов, `path`, `projectRoot` и порт сохраняются.
  Запрет MCP во всех многопапочных окнах лишил бы клиентов уже работающей интеграции
  с первой папкой. Одновременный доступ к нескольким проектам через MCP требует
  отдельного контракта.
- Если закреплённый проект удалён или внутри него открывается другая папка-проект,
  остановить свой endpoint. Правила MCP для произвольного пути записи разрешают
  потомков проектного корня. У экземпляра в другом окне, к которому мы можем
  присоединиться по `projectRoot`, собственная топология папок. Поэтому при вложенном
  корне запретить также ручной запуск и `reuse` в данном окне. Независимые соседние
  папки и обычные дочерние каталоги исходного проекта MCP не выключают.
  После снятия ограничения доступен запуск на том же закреплённом корне.
- Блокировка входа действует с начала изменения топологии, до асинхронного закрытия
  сессий и слушателя. Оконный координатор сериализует `start`, `stop`, `reuse` и
  `forceRestart` вместе с изменениями настроек и топологии. Каждый старт и диалог
  запоминают поколение разрешённой привязки. После `await` проверять его до публикации
  endpoint, принятия `reuse`, отправки `/shutdown` или нового bind. Если bind завершился
  для устаревшего поколения, закрыть именно этот слушатель до выхода из старта. При
  деактивации инвалидировать поколение, дождаться очереди и закрыть оставшиеся ресурсы.
  Уже принятые запросы сохраняют проект и текущие правила отмены.
  В состоянии `reuse/adopted` остановка освобождает собственную привязку, не
  останавливая владельца порта в другом окне. Loopback, Host/Origin и диалоги
  операций хранилища сохраняют свои условия.
- Существующий `LspManager` и BSL Analyzer MCP остаются оконными. Подготовку
  конфигурации привязать к папке, которую этот LSP обслуживал при старте окна, и
  сохранить один трекер её перезапуска при появлении основной конфигурации. Выбор
  папки UI и события соседних проектов не перезапускают клиент. При удалении корня
  подготовки остановить старый клиент перед возможным стартом на новом корне.
  Параллельное индексирование отдельных проектов несколькими LSP-сессиями за рамками
  #121.

## Этапы реализации

### 1. Устранить singleton секрета и проверять границы пути

- Файлы: `infra/fs/PathKey.ts`, `infra/repository/RepositoryService.ts`, `Container.ts`,
  `ui/commands/ext/ExtensionCommandRunner.ts`, его потребители из команд базы, CF/CFE,
  хранилища и процессных адаптеров MCP. Удалить `setProjectSecretStorage`, передавать
  секрет и зафиксированный `workspaceFolder` по цепочке. Выделить закрытие одного
  агентского кэша из оконной очистки. В `disposeCachedAgentOperationServices(root)` убирать
  только привязанный к этому корню промис и дожидаться его завершения перед освобождением.
- Тесты: одинаковые настройки A/B во временных папках, разные пароли из одного тестового
  хранилища, вызовы выполняются вперемешку. Старый пароль доступен с прежним ключом.
  Кейс `/a/project` и `/a/project-other`, граница тома, корень, потомок, нормализация
  и регистр на поддерживаемых платформах. Тест завершения одного кэшированного агента
  с соседним агентом и промисом запуска на границе процесса.
- Готово после компиляции, lint, связанных тестов DB/CF/CFE/MCP и прежнего пути одного
  проекта, сохранившего то же поведение команд.

### 2. Извлечь контекст и время жизни одного проекта

- Файлы: `Container.ts`, `extension.ts`, `ui/workspace/`, `infra/fs/ConfigLocator.ts`,
  `ui/support/SupportWatcher.ts`, `ui/readonly/`, существующие модули изменения файлов
  и модели Git. Сдвинуть проектные ресурсы из глобальных `context.subscriptions` в
  scope контекста. Включить явное завершение фоновых задач и защиту от устаревших
  публикаций. Прикладной bootstrap на этом этапе по-прежнему передаёт одну папку.
  Для закрывающейся папки не создавать повторный агентский/файловый контекст до конца
  предыдущих операций. Оконный guard, статус-бары, LSP, BSL и MCP регистрировать один раз.
- Тесты: создать два контекста в тестовом окружении с отдельными копиями реальной
  `example/2.21/src/cf` и парой одноимённых CFE из `example/2.21/src/cfe/EVOLC`.
  Проверить независимые `RepositoryService.lockStatus`, привязки, содержимое
  `state.json`, `.onecdev` и scoped-реакции на watcher. Для статусов использовать
  существующий тестовый источник или корпус из `repository-file-sync.md`.
  Удаление B диспоузит только его подписки и отменяет его не начатые действия.
  Проверить добавление B во время подготовки B, затем удаление и повторное добавление,
  и завершение старого таймера после снятия контекста. Для locator и маршрута проверить
  вложенный проект, вложение в активную выгрузку, общий префикс и алиас каталога.
- Готово после компиляции, lint и связанных тестов изоляции, обнаружения конфигураций,
  readonly и удаления ресурсов при сохранённом однопапочном bootstrap.

### 3. Перевести команды и панели на явный проект

- Файлы: `ui/commands/{CommandRegistry,_shared,ProjectCommandRegistry}.ts`,
  регистраторы `repository/`, `db/`, `ext/`, `project/`, `standalone/`,
  `search/` и остальные проектные регистраторы из `CommandRegistry`.
  Проверить все цепочки `executeCommand` из этих команд. Предохранитель владельца
  устанавливается на уровне проектного запуска, а запись во время изменения топологии
  проверяется на границах соответствующих путей в имеющихся потоках. Существующие
  функции хранилища остаются общими между редактором и MCP.
- Файлы UI: `ui/views/universal/`, `ui/views/properties/`, `ui/views/environment/`,
  `ui/views/standalone/`, `ui/views/repositoryHistory/`, `ui/views/metadataChanges/`,
  `src-ui/apps/universal/`, `src-ui/shared/protocol/`. Добавить источник выбора
  проекта и модель `{ projectId, name, path }` в состоянии панели. Проект меняется
  только по проверенному ключу, старые идентификаторы узлов и сообщений истекают.
  Кнопка выбора проекта показывается при нескольких папках. Прямые API панелей,
  которые открываются из команд, захватывают контекст на входе.
- Тесты: команда от узла A при выбранном B, URI вне рабочей области, отмена Quick Pick,
  единственный кандидат, явный устаревший узел, повторное открытие папки с тем же ключом.
  Два одинаковых `nodeId` из разных поколений панели и поздняя запись свойства.
  Смена проекта между подтверждением и окончанием захвата, открытием диффа и read-only.
  Тесты той же операции при удалении проекта до старта и после запуска внешней команды.
  Добавить B внутри выгрузки A после запуска дампа CF/CFE или полного получения из
  хранилища, до `syncDirectorySnapshot`. Замена каталога и пофайловый путь должны
  завершиться до записи, содержимое B должно сохраниться.
  Путь post-mutation и предупреждение о конфликте проверять на временной копии выгрузки
  через текущий арнес синхронизации. MCP-вызов с зафиксированным проектом остаётся
  прямым вызовом существующих потоков.
- Готово после компиляции, lint и тестов реестра команд, webview, guard, scoped readonly,
  а также возврата штатных результатов Ctrl+Shift+P на одной папке.

### 4. Включить многопапочную активацию и проверить окно целиком

- Файлы: `Container.ts`, `extension.ts`, `ui/workspace/`, `ui/mcp/V8McpServer.ts`,
  `ui/views/ai/AiMcpViewProvider.ts`, `ui/commands/ext/ExtensionCommandRunner.ts`,
  `infra/agent/DesignerAgentProcess.ts`, `package.json` для папочных настроек агента,
  `src-ui/apps/` для связанных панелей. Передать список папок, включить наблюдение
  за топологией, пересчитать обработчики и discovery для бывших/новых владельцев.
  Закрепить исходный проект встроенного MCP и сохранить оконную регистрацию LSP.
  Задать `scope: "resource"` для `onecdev.configuration.operationMode` и `onecdev.agent.*`,
  читать настройки по URI папки и включить проверку владельца SSH-порта.
- Тесты: integration-тест в `src/test/suite/` через существующий
  `@vscode/test-electron` или отдельная цель существующего E2E-раннера
  `src/test/e2e/`, если запуск основного тестового окна на workspace-файле
  меняет предусловия других тестов. Использовать временный `.code-workspace` с
  двумя копиями CF и CFE и посторонней папкой, одинаковыми именами и двумя отдельными
  привязками. Проверить прямые вызовы зарегистрированных команд, переключение панели,
  добавление/удаление не первой папки, отсутствие повторной регистрации, различие
  readonly у открытых BSL A/B. MCP проверять при смене проекта в UI, добавлении
  независимой папки, вложенного корня и удалении исходного проекта. Проверить
  доступ только к закреплённому проекту, остановку без подмены корня и отсутствие
  автоперепривязки после перезапуска extension host в той же рабочей области.
  Проверить удаление корня во время bind или probe и подтверждение старого диалога
  после добавления вложенной папки. Поздний слушатель закрыт, чужой endpoint не принят,
  `/shutdown` не отправлен. Проверить агент A → B с тем же портом и учётными данными,
  независимыми портами, чужим занятым портом и `autoStart: false` с явными и унаследованными
  настройками. Проверить освобождение порта после закрытия A и ошибочного старта.
  Для режима одного проекта проверить неизменность работы MCP, старт/стоп, старые
  секреты, конфиги, миграцию .onecdev и базовый цикл генерации из существующего E2E.
- Готово после `npm run compile`, `npm run lint`, связанных тестов, итогового
  `bash .claude/scripts/qa-gate.sh origin/main` и ревью. `documenter` обновляет
  разделы [архитектуры](../architecture.md#точка-входа),
  [навигации](../metadata-navigator.md), [привязки и статусов](../repository-file-sync.md#привязка-к-хранилищу-envjson--autumn-propertiesjson)
  и [жизненного цикла MCP](../mcp-server-lifecycle.md), фиксирует выбор папки и
  границу поддержки LSP/MCP.

Проектное решение для согласования перед реализацией — одна выбранная папка в
навигаторе, явный выбор в палитре при нескольких кандидатах и закрепление
встроенного MCP за исходной папкой окна. Критические сценарии при ревью — уже начатая операция после смены
выбранной папки, вложенная папка внутри выгрузки, устаревшие сообщения webview и
изоляция паролей/статусов.
