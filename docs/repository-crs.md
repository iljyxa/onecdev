# Клиент протокола сервера хранилища (crs)

Клиент `crserver` (tcp и http/https) без запуска платформы: рукопожатие по версии, статистика объектов
(статусы захвата), методы истории и пользователей. Перенесён из проекта
[vscode-1c-repository-tools](https://github.com/iljyxa/vscode-1c-repository-tools) (коммит `8391ab0`, личный проект
автора onecdev) в iljyxa/onecdev#116 (этап 1). Исследования — [research/crs/](./research/crs/) (датированы,
правке не подлежат); снятый трафик — `example/crs/` ([README](../example/crs/README.md)); потребитель —
[сетевой источник статусов](./repository-file-sync.md#статусы-захватов-с-сервера).

Нумерация решений **сохранена из исходного проекта** (3, 6, 7, 8, 9, 14): на неё ссылаются комментарии кода
(`CrsDepot.ts` — решение 8, `CrsHistory.ts` — решение 3) и `qa-gate.sh`. Не переименовывать.

## Решение 3. Гибрид: протокол — метаоперации, платформа — содержимое

По протоколу — статусы захвата, история, пользователи (захват/отпуск — на следующих этапах); помещение и
получение содержимого объектов — через платформу (Конфигуратор в пакетном режиме). Содержимое лежит во
внутреннем позиционном формате платформы; его перевод в XML-выгрузку — повторная реализация выгрузки
Конфигуратора ([04-crs-protocol.md](./research/crs/04-crs-protocol.md)).

**Исключение для истории.** Запрет касается содержимого объектов — base64 в `<crs:data>` (контейнер
`0x11223344`) и `crs:snapshots`. Ответ `DevDepot_devDepotReport` тоже обёрнут в `<crs:data>`, но внутри открытый
XML (`objectVersions`, `depotVersions`) — он читается **только** в `CrsHistory.ts`
([06-crs-history.md](./research/crs/06-crs-history.md)). Механизм — три sanity-проверки `qa-gate.sh`:

1. `crs:snapshots|commitObjects|updateObjects|11223344` в `src` кроме тестов — 0;
2. `crs:data` в `src` кроме тестов и `CrsHistory.ts` — 0;
3. `base64|atob(` в `CrsHistory.ts` — 0 (читатель истории не может превратиться в разборщик содержимого).

Отвергнуто: помещение только модулей по протоколу (риск повредить общее хранилище); разрешить `crs:data` во
всём `infra/repository/crs/` (запрет перестал бы ловить случайный разбор содержимого).

## Решение 6. Транспорт tcp: соединение на вызов

1. Одно соединение на вызов: подключиться, получить приветствие сервера, отправить приветствие клиента и кадр
   одной записью, прочитать один ответ, закрыть сокет.
2. Ответ читается до `Content-Length` байт; терминатор `6653b2a6` и байты после тела **не читаются**. Сервер
   терминатор *запроса* ждёт — клиент его шлёт, зависший вызов ловит дедлайн.
3. Статус не 200 — ошибка транспорта `status`, адаптер переводит её в `server-error` (в старом клиенте onecdev — `protocol`; изменение осознанное).

Почему: итог вызова однозначен, сокет закрывается при любом исходе; при соединении на вызов проверка
терминатора ответа ничего не защищает и превращала бы полученное тело в отказ
([08-crs-tcp-framing.md](./research/crs/08-crs-tcp-framing.md), A1/A3).

**Адаптация onecdev (расходится с решением 6.2 исходника).** Приветствие сервера `53f5c61a7b` **не сверяется по
байтам** — проверяется только длина (5 байт), как в прежнем клиенте onecdev: байты сняты только на 8.5.1, а
8.3.x — основная аудитория; жёсткая сверка ломала бы подключение при другом приветствии. Исходник сверял и давал
`protocol`.

## Решение 7. Конверт, свой XML-ридер, классификация по clsid + код, рукопожатие

1. Конверт, разбор ответа и исключений — `CrsEnvelope.ts`/`CrsException.ts`; `CrsClient` зависит только от
   контракта `CrsTransport`, поэтому tcp и http подключаются без правок конверта. `buildCallBody` побайтно
   воспроизводит снятые запросы корпуса.
2. Свой узкий XML-ридер вместо `fast-xml-parser`: нужен разбор с пространствами имён и только пятью
   предопределёнными сущностями (XXE невозможна), без DTD/CDATA/комментариев; XML `crserver` машинный.
3. Вид отказа — пара **clsid + код** (второй элемент корня скобочного текста), не текст: он локализован. Для
   clsid хранилища `3ccb2518`: код 4 — `auth-failed`, 1 — `depot-not-found`, 17 — `version-mismatch`. VRS
   (статус не 200): `c593fe3b` — `bad-request`, прочие — `rejected`; пустое тело — `unknown-method`;
   нераспознанная пара — `server`.
4. Рукопожатие: один раз на экземпляр `CrsClient`, кэшируется только успех; запрос `openDevDepot` с
   `version="0.0.0.0"`, версия сервера — из исключения `version-mismatch`. На обычном вызове
   `version-mismatch` сбрасывает кэш, автоповтора нет.
5. Секреты: `maskCrsSecrets` маскирует `crs:auth password` и `crs:password value` и в запросах, и в **ответах**
   (`devObjectsStatistic`, `depotUsers` возвращают хеши паролей всех пользователей). В сообщениях и `details`
   ошибок тел запросов и хеша нет.

**Уточнение onecdev: версия сервера — структурно.** Версия берётся как последний `N.N.N.N` из записи
исключения с clsid `9f06d311-1431-4a54-bd6f-fa93c4d4c471` (вложенная запись о версии), а не по тексту
сообщения; текст остаётся запасным путём (локализация сервера). Причина: в тексте версия клиента стоит раньше
версии сервера, а язык сообщений зависит от платформы
([05-crs-api.md](./research/crs/05-crs-api.md), «Рукопожатие по версии»). Подсказка версии не вида `N.N.N.N`
(`isCrsServerVersion`) заменяется на рукопожатие `0.0.0.0`.

Отвергнуто: `fast-xml-parser` и прочие XML-зависимости; классификация по тексту; автоповтор при
`version-mismatch` и single-flight рукопожатия (скрытое состояние без подтверждённой нужды — повтор делает
адаптер источника статусов, один раз).

## Решение 8. Методы чтения: функции над CrsClient, модели без хешей, `bind` не нужен

1. Методы — функции над `CrsClient` без состояния (`openDevDepot`, `authenticate`, `depotInfo`, `bind` —
   `CrsDepot.ts`; `devObjectsStatistic` — `CrsStatistic.ts`). Читатели строгие: нет обязательного элемента —
   `CrsFormatError`, который `decodeReturn` переводит в `CrsCallError('malformed-response')`.
2. Методы принимают `CrsAuth` с готовым хешем пароля; открытый пароль в `infra/repository/crs` не попадает.
3. Модели не содержат хешей паролей: из `crs:userInfo` и `crs:users` хеш отбрасывается.
4. Даты — строки как есть, без пояса; `rights` — число без интерпретации (65535/3/0 проверены только на 8.5.1);
   `lock` объекта заполняется только при `revised=true`.
5. **`DevDepot_bind` для чтения не нужен и не вызывается**: статистика, история и список пользователей дают
   побайтно одинаковые ответы без `crs:bind`, со случайным `bindID` и от пользователя `ReadOnly`; сервер не хранит
   состояние сеанса. `bind` с неизвестным `bindID` отказывается (код 10/11), а `force=true` заменил бы привязку
   пользователя ([05-crs-api.md](./research/crs/05-crs-api.md), «Привязка `crs:bind` для чтения»).

Отвергнуто: класс-сеанс (порядок вызовов — сценарий, не протокол); `bind` в сценарии чтения.

## Решение 9. Транспорт http: node:http(s), соединение на вызов, адрес — единая точка

1. `node:http`/`node:https`, не собственное кадрирование. Чистая часть (endpoint, заголовки, опции) —
   `CrsHttpFraming.ts`.
2. Одно соединение на вызов: `agent: false`, `Connection: close`, `req.destroy()` при любом исходе; пять
   заголовков задаются явно в порядке пробы `http/probe-valid`; дедлайн — общий `setTimeout` на весь вызов (с DNS
   и подключением). Закрытие соединения до ответа определяется по событию `end` сокета, а не по тексту ошибки.
3. TLS — только `ca`, `rejectUnauthorized` (по умолчанию `true`), `servername` (для DNS-имён). Нового вида ошибки
   `tls` нет: ошибка TLS — `unavailable` с `cause`; адаптер источника классифицирует её по кодам.
4. Адрес разбирается в `CrsAddress.ts` (`parseCrsAddress`), транспорт и клиент по нему создаёт `CrsConnect.ts`.
   Учётные данные в адресе **отвергаются** (не вырезаются: пароль остался бы в настройках), как и query/fragment
   (в них бывают токены). Исходная строка адреса не попадает в сообщения и поля ошибок.
5. `endpoint.path` — путь до `.1ccr` включительно; alias идёт в конверт, не в путь.

**Адаптации onecdev.**

- **Alias по умолчанию `maincr`** (`CRS_DEFAULT_ALIAS`) для http без alias — прежнее поведение onecdev. Исходник
  (решение 9.6) требовал alias обязательно: Конфигуратор снят только с ним.
- **Строже разбор адреса**: userinfo, query, fragment, пустой сегмент пути, порт 0 — `CrsAddressError`.
  Сообщение `invalid-address` не содержит адреса.
- **Коды отказов http.** «socket hang up» до ответа — `closed`, и адаптер сводит его к `protocol` (раньше —
  `unavailable`). VRS-исключения публикации: `bad-request` → `protocol`, `rejected` → `server-error`.

Следствия: VS Code в Extension Host подменяет `http`/`https` (`http.proxySupport`) — защита явные
`Connection: close` и `destroy`; при `HTTP_PROXY` без исключения для `127.0.0.1` тесты на воспроизведении могут
уйти через прокси (`NO_PROXY=127.0.0.1`). Пул keep-alive потребует отдельного решения.

Отвергнуто: собственное кадрирование HTTP; пул keep-alive; вырезание userinfo; отдельный вид ошибки `tls`.

## Решение 14 (протокольная часть). История и пользователи

Здесь только протокол; сервис, панель и постраничная загрузка — этап 2 (iljyxa/onecdev#117).

1. `DevDepot_devDepotReport` (`CrsHistory.ts`) и `UserManager_depotUsers` (`CrsUsers.ts`) — функции над
   `CrsClient` по образцу решения 8. Разбор `crs:data` — только в `CrsHistory.ts`, без base64 (решение 3). Модели
   без хешей паролей, хешей версий объектов (`info/version/original|local`) и `externals`; `processOrder` не
   читается.
2. **Правило `mask`**: без объектов — `1` (как Конфигуратор), объекты без диапазона номеров — `4`, с диапазоном —
   `5`. Запросы побайтно совпадают со снятыми пробами. `objectIds` — uuid, порядок сохраняется; пустой список или
   не uuid — `RangeError`; `recursive` без `objectIds` — `RangeError`.
3. **История объекта — серверный отбор**: `objectIds: [id]` и `recursive: true` (объект и потомки по `parentID`);
   клиентский отбор по `parentID` не нужен.
4. **Схлопывание повторов**: при нескольких объектах или `recursive` сервер повторяет версию у каждого
   отобранного объекта — разбор оставляет первое вхождение по `verNum`.
5. **Постраничность**: `DevDepot_devDepotVersions` — лёгкий список номеров по тому же фильтру; границы страницы —
   реальные номера из списка (номера объекта разрежены: 1, 2, 3, 6), не арифметика. `unknown-method` на списке
   — откат на один `devDepotReport` целиком (8.3.x не проверялось).
6. `bind` не нужен ни истории, ни пользователям (решение 8, п. 5).

Даты в фильтре не поддерживаются (диапазон номеров — да); даты только разбираются из ответа.

## Адаптации onecdev: сводка

Что изменено относительно исходника и прежнего клиента onecdev (`NetworkRepositoryLockStatusSource` и
`parseCrsAddress` до #116):

- адаптер `NetworkRepositoryLockStatusSource.ts`: таблицы видов ошибок → `RepositoryLockStatusErrorCode`; один
  повтор с версией сервера из `version-mismatch`; TLS классифицируется по кодам; таймаут 60 с, лимит 128 МиБ;
  `removed=false` в запросе статистики;
- сообщение `invalid-address` без адреса; userinfo/query/fragment/пустой сегмент/порт 0 отклоняются;
  alias `maincr` для http — см. решение 9;
- tcp: статус ≠ 200 → `server-error`; приветствие сервера — только длина (решение 6);
- строгий разбор статистики и скобочного текста (`OneCBracketText.ts` — общий для crs и 1CD);
- `clientId` приветствия клиента случайный, один на экземпляр транспорта (как у процесса 1cv8): рукопожатие и вызов через один клиент идут разными соединениями с одним `clientId`;
- версия сервера из исключения — структурно (решение 7).

## Не проверено

- `crserver` 8.3.x: все байты и коды сняты на 8.5.1 (приветствие, версия, права, `devDepotVersions`). Расхождение
  проявится отказом рукопожатия/кадрирования, а не молча.
- https на стенде: проверяются разбор адреса, опции запроса и ветка `https.request` (ECONNREFUSED, TLS поверх
  открытого ответа).
- Basic-авторизация apache перед публикацией `.1ccr`.
- Вложенный alias (`tcp://srv/a/b` принимается как есть), порт tcp 1542 по умолчанию (из документации 1С).
- Таймаут простоя соединения на сервере, pipelining, мусорное приветствие клиента
  ([08-crs-tcp-framing.md](./research/crs/08-crs-tcp-framing.md), «Не проверено»).
