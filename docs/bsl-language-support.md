# Языковая поддержка BSL

## Назначение

Языковая поддержка BSL работает только через внешний LSP-сервер `bsl-analyzer`.
Расширение отвечает за жизненный цикл клиента: находит или скачивает бинарник,
запускает его в режиме `lsp`, подключает к `.bsl`-файлам и показывает состояние
в статус-баре.

Встроенного tree-sitter сервера в проекте нет. Ветка `built-in`, wasm-грамматики
и локальные провайдеры completion/hover/diagnostics удалены, чтобы не было двух
источников поведения.

## Архитектура

```
VS Code Extension Process (dist/extension.js)
    ├── LspManager
    │   ├── BslAnalyzerService      # установка, обновление, путь к бинарнику
    │   └── BslAnalyzerStatusBar    # состояние сервера в статус-баре
    │
    └── LanguageClient (stdio)
        └── bsl-analyzer lsp
```

`LspManager` читает настройку `onecdev.lsp.mode`. Клиент подписывается на `.bsl`-документы
без `synchronize.fileEvents` (`buildBslAnalyzerDocumentOptions`, `lsp/LspManager.ts`): сервер не
обрабатывает `workspace/didChangeWatchedFiles` и следит за файлами сам, поэтому события клиента —
лишний трафик на каждую выгрузку во временный каталог операции. Там же
`revealOutputChannelOn: Never`: сбой запроса (например, `-32603` на `documentHighlight` при
рассинхроне текста у сервера) пишется в канал «BSL Analyzer», но не всплывает уведомлением —
иначе фоновые запросы на каждое движение курсора давали поток окон (#105).

Допустимые значения:

| Значение | Поведение |
|---|---|
| `bsl-analyzer` | Запустить внешний `bsl-analyzer lsp` |
| `off` | Не запускать языковой сервер |

## Структура модуля

Откройте модуль `.bsl` или `.os` и раскройте «Структуру» (Outline) в проводнике VS Code.
Представление можно перетащить во вторичную боковую панель.

При запущенном bsl-analyzer символы предоставляет языковой сервер. Пока он запускается,
остановлен или отключён, встроенный резервный провайдер показывает области, процедуры,
функции и переменные уровня модуля. Он также работает для отдельных файлов в окне
без открытой рабочей папки.

## Настройки

| Настройка | Назначение |
|---|---|
| `onecdev.lsp.mode` | Включает `bsl-analyzer` или отключает LSP |
| `onecdev.bslAnalyzer.autoUpdate` | Проверять обновления при запуске |
| `onecdev.bslAnalyzer.path` | Использовать пользовательский путь к бинарнику |

Если `onecdev.bslAnalyzer.path` пустой, расширение хранит скачанный бинарник
в `globalStorageUri/bsl-analyzer`.

## Запуск

`LspManager.startWithAutoUpdate()`:

1. Запускает LSP по текущей настройке.
2. При режиме `bsl-analyzer` вызывает `BslAnalyzerService.ensureBinary()`.
3. Создаёт `LanguageClient` с командой `bsl-analyzer lsp`.
4. Подписывает клиент на `file://` документы языка `bsl`.
5. При включённом `autoUpdate` планирует проверку обновления через 30 секунд.

Для диагностики доступны команды:

| Команда | Назначение |
|---|---|
| `onecdev.bslAnalyzer.showMenu` | Открыть меню управления |
| `onecdev.bslAnalyzer.restart` | Перезапустить LSP |
| `onecdev.bslAnalyzer.update` | Проверить обновления |
| `onecdev.bslAnalyzer.showOutput` | Показать лог |

### Перезапуск при появлении основной конфигурации (issue #104)

`bsl-analyzer` выбирает корень конфигурации только один раз при старте: если тогда основной
выгрузки `src/cf/Configuration.xml` ещё не было, сервер индексирует и отслеживает всю рабочую
область целиком, включая `.onecdev/**` — на Windows его watcher держит дескрипторы этих файлов,
из-за чего удаление временных каталогов операций (хранилище, импорт) падает с `ENOTEMPTY`/`EPERM`.

`Container.reloadEntries()` после перестроения дерева вызывает `restartLspOnRootsChange`, который
через `BslAnalyzerRootTracker` (`infra/environment/BslAnalyzerRootTracker.ts`, чистый домен без
`vscode`) перезапускает `LspManager` **ровно** при переходе «нет основной конфигурации → есть»:

- на bootstrap (первое наблюдение) — не перезапускает: сервер и так стартует с текущим составом;
- появление/переименование cfe без основной cf — не перезапускает: сервер `bsl-analyzer` выбирает
  корень по `.toml`, а не по составу расширений;
- исчезновение основной конфигурации — не перезапускает (сервер уже проиндексирован так, как есть,
  откатывать нечего);
- `onecdev.lsp.mode = off` — не перезапускает, при последующем включении сервер стартует заново
  и сам увидит актуальный состав.

`BslAnalyzerRootTracker.observe()` хранит только факт «есть/нет основной конфигурации» между
вызовами и не хранит `vscode`-состояние — логика решения (`decideBslAnalyzerRestart`) покрыта
unit-тестами домена, а сам вызов рестарта — тонкая обвязка в `Container.ts`.

Если основной конфигурации нет вовсе (только cfe) или перезапуск не удался, сервер индексирует весь
workspace; от этого случая защищает исключение служебного каталога в `bsl-analyzer.toml` (см. ниже).

### Исключение служебного каталога `.onecdev` (issue #112)

Служебный каталог `.onecdev` (снимки, резервные копии слияния, временные выгрузки) добавляется в
`[source].exclude` файла `bsl-analyzer.toml`. `.v8vscedit` не исключается: он мигрируется в `.onecdev`
до старта сервера. Ключ поддерживается с `bsl-analyzer` v0.2.85 (itrous/bsl-analyzer#153); разбор
конфига у сервера строгий, поэтому более старая версия с этим ключом проект не загрузит. Отсюда политика
трёх состояний по версии сервера (`infra/environment/BslAnalyzerToml.ts`, чистый домен):

| Версия | Действие с файлом |
|---|---|
| `>= 0.2.85` | служебный элемент добавляется; только аддитивно, пользовательские элементы `exclude` сохраняются |
| `< 0.2.85` (откат) | удаляется только служебный элемент; опустевший массив уходит вместе с ключом; если остались пользовательские элементы — предупреждение `[lsp][warn]` в лог |
| неизвестна | файл не меняется; при наличии `exclude` — предупреждение в лог |

Определение версии (`infra/environment/BslAnalyzerVersion.ts`):

- автоскачанный сервер — из `version.txt`;
- пользовательский путь `onecdev.bslAnalyzer.path` — проба `<binary> --version` (stdin закрыт, таймаут
  5 с, версия — первый токен вида `X.Y.Z` в stdout; вывод v0.4.6: `bsl-analyzer 0.4.6\nbsl-analyzer-launcher
  0.4.6`). Ассет релиза — загрузчик: при первом запуске он сам скачивает основной бинарь в
  `~/.bsl-analyzer/bin`. Если проба упёрлась в таймаут во время этой загрузки, версия считается
  неизвестной (безопасное состояние); прерванная загрузка частичного файла не оставляет, следующий
  запуск докачивает.

Момент сверки — перед каждым стартом клиента LSP (`LspManager`: первый старт, после скачивания/
обновления, смены пути или режима, перезапуск по #104), **до** запуска процесса, чтобы сервер сразу
читал итоговый файл. Выполняется только в инициализированном проекте и при существующем toml; при
`onecdev.lsp.mode = off` не выполняется. Ошибка подготовки пишется в лог и старт не срывает. Механизм
неотключаемый: вручную удалённый служебный элемент вернётся при следующем старте.

`updateSource` (подключение расширения, `BslAnalyzerConfigService`) меняет в `[source]` только `root` и
`extensions`; остальные записи (`exclude`, `exclude_globs`, комментарии) сохраняются. Формат файла
(BOM, EOL) сохраняется, без изменений файл не переписывается. Известное ограничение — корневой `source`
без заголовка `[source]`: #139.

## Открытие BSL-модулей

Модули открываются напрямую как `file://` документы. Виртуальная схема `onec://`
не используется.

Readonly для модулей под замком поддержки или хранилища обеспечивают:

1. `OpenModuleCommand` — сразу помечает редактор readonly при открытии из дерева. Поддержка
   проверяется по XML владельца, а хранилище — по единице узла (`resolveRepositoryEditProbePath`):
   модуль формы объекта редактируем при захвате самой формы, независимо от захвата владельца. Та же
   проверка запрещает создание отсутствующего модуля.
2. `BslReadonlyGuard` — перехватывает открытие `.bsl` файлов с диска.

### Определение режима поддержки BSL-модуля

Замок поддержки (`SupportMode`: `None`/`Editable`/`Locked`/`Removed` — трактовка кодов
`ParentConfigurations.bin` и формат файла подробно описаны в
[architecture.md](./architecture.md#режим-поддержки-поставщика-parentconfigurationsbin)) хранится по
UUID объекта, а UUID нужно взять из XML — модуль сам по себе его не содержит.
`SupportInfoService.resolveOwnerXml` (`infra/support/SupportInfoService.ts`) находит нужный XML
по пути к `.bsl`-файлу. Тем же путём режим получают служебные XML внутри `Ext/` (`Form.xml`,
`Template.xml`, `Rights.xml`, `Help.xml`, `CommandInterface.xml`): атрибута `uuid` у них нет, и без
резолва к владельцу вкладка такого файла объекта «не редактируется» считалась бы свободной. Файлы
корневого `Ext/` конфигурации (модули приложения и сеанса, `Help.xml`, интерфейс) берут режим
`Configuration.xml` корня (#126). Для остальных:

- модуль подчинённого со своим XML (`.../<Папка>/<Имя>/…/Ext/...`, где `<Папка>` — один из подкаталогов
  `SUBORDINATE_OBJECT_FOLDERS` из [`infra/fs/SubordinateObjectLayout.ts`](../src/infra/fs/SubordinateObjectLayout.ts):
  Forms, Templates, Recalculations, Tables, Cubes, DimensionTables, Subsystems) — путь между владельцем и
  `Ext` может содержать несколько вложенных пар «папка/имя» (например, таблица внешнего источника →
  форма таблицы, куб → таблица измерения); режим берётся из XML **самого глубокого** существующего
  подчинённого этой цепочки (`.../<Папка>/<Имя>.xml`);
- иначе, или если ни один подчинённый цепочки не имеет собственного XML (команда объекта и т.п.) —
  режим определяется по XML объекта-владельца.
  Владелец ищется через `findObjectXmlInFolder` (`infra/fs/ObjectLocation.ts`): сначала глубокая форма
  `<Папка>/<Имя>/<Имя>.xml`, затем плоская `<Папка>/<Имя>.xml`; стандартная выгрузка Конфигуратора —
  плоская, поэтому без этого поиска режим поддержки BSL-модулей почти никогда не определялся.
- если владелец не найден — режим `SupportMode.None`, событие пишется в лог как
  `[support] XML объекта не найден: <папка>/<имя>`. Исключение — конфигурация с флагом «изменения
  запрещены» в заголовке `.bin`: тогда `SupportInfoService.getSupportMode` возвращает `Locked` для
  ЛЮБОГО файла под её корнем ещё до поиска XML владельца, поиск XML в этом случае не выполняется
  вовсе (см. [architecture.md](./architecture.md#режим-поддержки-поставщика-parentconfigurationsbin)).

Режим команды объекта — приближение: у `<Command uuid=…>` внутри XML владельца свой UUID, и его
режим в `ParentConfigurations.bin` в принципе может отличаться от режима владельца, но поиск UUID
дочернего элемента внутри XML владельца не выполняется — модуль команды всегда наследует режим
владельца.

## Сборка

Webpack собирает только клиент расширения, тестовый entry и CLI:

```javascript
entry: {
  extension: './src/extension.ts',
  'test/runTests': './src/test/runTests.ts',
  'cli/onec-tools': './src/cli/onec-tools.ts',
}
```

Отдельного `dist/server.js` и копирования wasm-файлов нет.
