# Протокол сервера хранилища: эксперимент с помещением и получением

Дата эксперимента: 2026-09-29.

## Цель

Выяснить, что передаётся между Конфигуратором и сервером хранилища (`crserver`) при помещении
и получении объектов, и решить, можно ли реализовать эти операции полностью по протоколу, без
платформы.

## Стенд

- Платформа 8.5.1.1529 (`/opt/1cv8/x86_64/8.5.1.1529`): `crserver`, `1cv8` в пакетном режиме
  через `xvfb-run`, `ibcmd`. У 8.3.27 в этой установке `crserver` нет.
- Конфигурация — фикстура `example/2.21/src/cf` из v8vscedit (стоит на поддержке; правило
  по умолчанию «не редактируется», `Справочник.Контрагенты` снят с поддержки).
- Транспорт — tcp. Каждая команда Конфигуратора шла через свой записывающий tcp-прокси.
- Скрипты и образцы остались в исходном проекте (`research/crs-capture/`).

## Сценарий (все шаги успешны)

| Шаг | Команда | Кто |
|---|---|---|
| 01-create | `/ConfigurationRepositoryCreate` — создание хранилища из базы A | Admin |
| 02-adduser | `/ConfigurationRepositoryAddUser` Petrov/123, права LockObjects | Admin |
| 03-bind-B | `/ConfigurationRepositoryBindCfg` новой базы B — полное получение | Petrov |
| 04-lock | `/ConfigurationRepositoryLock` `Справочник.Контрагенты` | Petrov |
| 04b-load-partial | дописать строку-маркер в `ObjectModule.bsl`, `/LoadConfigFromFiles -partial` | Petrov |
| 05-commit | `/ConfigurationRepositoryCommit` — помещение | Petrov |
| 06-update-A | `/ConfigurationRepositoryUpdateCfg -force` в базе A — получение изменений | Admin |

Попутные наблюдения:

- Частичная загрузка в привязанную базу требует параметров хранилища
  (`/ConfigurationRepositoryF` и др.), иначе Конфигуратор не видит захват.
- Объект с правилом поддержки «не редактируется» загрузить нельзя даже после захвата
  («редактирование объекта метаданных … запрещено»).

Сценарий прогнан дважды (`out/`, `out2/`) для проверки детерминированности.

## Результаты

### Транспорт

- tcp: сервер шлёт 5 байт приветствия (`53f5c61a7b`, постоянные); клиент — `224855b5` + 16
  байт случайного UUID v4, одинакового в пределах процесса Конфигуратора. Затем кадры
  `POST  HTTP/1.1` с `Content-Length` и терминатором `6653b2a6`. Обмена ключами нет. Побайтный
  разбор кадров и рукопожатия — [08-crs-tcp-framing.md](08-crs-tcp-framing.md).
- Тело — XML `crs:call` (UTF-8 с BOM, пространство имён `http://v8.1c.ru/8.2/crs`),
  аутентификация — `crs:auth user=… password=<md5 от пароля в UTF-16LE>`. Ответ —
  `crs:call_return` или `crs:call_exception` (base64 скобочного текста).

### Вызовы по шагам

| Операция | Ключевые методы |
|---|---|
| Любая | `DevDepotAdmin_openDevDepot`, `DevDepot_authenticate`, `DevDepot_depotInfo`, `DevDepot_bind`, `DevDepot_devObjectsStatistic` |
| Создание | `DevDepotAdmin_createDevDepot` (вся конфигурация — 426 КБ тела) |
| Пользователь | `UserManager_addUser`, `DevDepot_getParams` |
| Привязка | `DevDepot_devObjectsVersionEx`, `DevDepot_latestVerID`, `DevDepot_updateInfo` |
| Захват | `DevDepot_reviseDevObjects` |
| Помещение | `DevDepot_latestVerNum`, `DevDepot_devObjectInfoEx`, `DevDepot_commitObjects` (8,7 КБ), затем `DevDepot_reviseDevObjects` |
| Получение | `DevDepot_updateObjects` (клиент шлёт версии своих 108 объектов, сервер отвечает снимками изменённых) |

Служебные поля (uuid, `classID`, `verNum`, хеши версий `original`/`local`, `parentID`,
`action`) лежат в открытом XML. Данные объектов — один base64-узел `<crs:data>`
(в `crs:snapshots` при получении и создании, в `crs:params` при помещении).

### Упаковка данных

**Получение и создание** — контейнер:

```
u32 0x11223344 | u32 версия = 2 | u32 число записей
далее блоки: u64 длина | данные
```

Блок — либо открытый скобочный текст (UTF-8 с BOM; заголовки записей с uuid, классом,
родителем, именем), либо raw deflate. Для одного объекта в дельте получения было 6 записей /
7 блоков; в конце — блок с SHA1-хешами (`"1a38df58…"`) и бинарный индекс (снова начинается с
`0x11223344`), затем 64 байта хвоста.

**Помещение**:

```
18 байт заголовка 0201534b6ff4888dc14ea0d5ebb6bda0a70d | raw deflate {
  u64 длина | манифест изменений (скобочный текст: uuid, класс, родитель, имя,
              версии в base64, зависимости)
  u32 0 | u64 длина | тот же контейнер 0x11223344
}
```

Заголовок побайтно совпал в двух прогонах с разным содержимым (4256 и 4010 байт) — это
константа формата, не контрольная сумма. Смысл не установлен.

Шифрования нет. Передаётся только дельта: при помещении и получении — 4–5 КБ по одному
изменённому объекту против 420 КБ при создании.

### Содержимое объекта

Маркер, дописанный в модуль, найден внутри блока модуля и в помещении, и в получении.

| Часть | Формат | Сложность |
|---|---|---|
| Модули BSL | v8-контейнер (как внутри `.cf`: заголовки `00000018 00000018 7fffffff`) с файлами `info` и `text` | простая |
| Макеты-XML (СКД, XDTO и т. п.) | XML как есть | простая |
| Свойства объекта, реквизиты, типы | внутренний позиционный скобочный формат | **сложная** |
| Формы, табличные документы, права ролей | внутренний формат | **сложная** |
| Служебные блоки | SHA1 блоков и индекс | средняя |

Пример начала описания `Справочник.Контрагенты` в хранилище:

```
{1,
{57,5efc9a0f-…,fb160d7d-…,dfa3b5de-…,…,
{0,
{3,
{1,0,2c53bb9d-bda3-431e-95f5-0d4145c8ac74},"Контрагенты",
{1,"ru","Контрагенты"},"",0,0,00000000-0000-0000-0000-000000000000,0}
},2,1,
{0,0},1,1,1,0,9,1,25,1,1bda8320-…,
```

В выгрузке те же данные — именованный XML (`Catalogs/Контрагенты.xml`, 271 строка:
`<Hierarchical>`, `<HierarchyType>`, `<LevelCount>` и т. д.).

## Выводы

1. Транспорт, конверт и упаковка — простые и полностью разобраны.
2. Содержимое объектов — внутренний формат платформы, тот же, что внутри `.cf`. Перевод его в
   XML-выгрузку и обратно — это повторная реализация `DumpConfigToFiles`/`LoadConfigFromFiles`
   для каждого вида метаданных, форм и макетов, для каждой версии платформы. Формат не
   документирован, ошибка портит общее хранилище команды.
3. **Решение: гибрид.** По протоколу — метаоперации (статусы, захват, отпуск, история, версии,
   пользователи, метки, состав изменений версии). Помещение и получение содержимого — через
   платформу.
4. Рассматривалась возможность помещать изменения только модулей по протоколу (подменой блока
   модуля в снимке объекта). Решено не развивать: требует разгадки 18-байтного заголовка и
   схемы хешей, выигрыш не оправдывает риска.

## Ограничения эксперимента

- Платформа 8.5.1; эксперимент шёл по tcp. Http (публикация `.1ccr` через wsap) снят позже для захвата и
  отпуска — те же тела ([07-crs-http.md](07-crs-http.md)); помещение по http не снималось.
- Разобран один объект — справочник с модулем; формы и макеты видны только в данных создания.
