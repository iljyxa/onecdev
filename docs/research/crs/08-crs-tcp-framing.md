# Протокол `crs` по tcp: кадрирование и рукопожатие

Дата: 2026-09-29. Платформа 8.5.1.1529 (`crserver`, `1cv8`). Источник — сырые потоки, снятые
`node example/tools/crs/capture-tcp-raw.mjs` в `example/crs/8.5.1/tcp-raw/` (описание —
[example/crs/README.md](../../../example/crs/README.md)). Байты в файлах не правлены; каждый факт ниже
указан с файлом, в котором его можно проверить (`xxd <файл>`). Пути даны относительно `tcp-raw/`.

Что было известно до этого ([04-crs-protocol.md](04-crs-protocol.md)): приветствие сервера `53f5c61a7b`,
клиента — `224855b5` + 16 байт, кадры `POST  HTTP/1.1` с `Content-Length` и терминатором `6653b2a6`.
Ниже — уточнения, которых не хватало для реализации транспорта tcp.

## A1. Терминатор `6653b2a6`

- Стоит **после тела** и **не входит в `Content-Length`**, у запроса и у ответа.
  `wrong-password/conn-01.c2s.bin` (361 байт) = 20 (приветствие клиента) + 95 (заголовки) + 242
  (`Content-Length: 242`) + 4 (`66 53 b2 a6` в конце файла). `wrong-password/conn-01.s2c.bin` (518 байт)
  = 5 (приветствие сервера) + 71 (заголовки) + 438 (`Content-Length: 438`) + 4 (терминатор).
- Сервер **ждёт терминатор**, одного `Content-Length` ему мало: `probe-no-terminator` — полное тело
  по `Content-Length` без терминатора, за 3 с в `response.bin` только приветствие (5 байт);
  `probe-late-terminator` — тот же кадр, терминатор отдельной записью через 3 с, и только после него
  приходит ответ (`order.json`: `s2c 5`, `c2s 20` (приветствие клиента), `c2s 337`, `c2s 4`, затем `s2c 513`).
- Для клиента: кадр ответа — заголовки до `\r\n\r\n`, `Content-Length` байт тела, затем ровно
  `6653b2a6`; иное — нарушение протокола.

## A2. Заголовки запроса

Точный набор и порядок у Конфигуратора, одинаковый у `openDevDepot` и `authenticate`
(`wrong-password/conn-01.c2s.bin`, `conn-02.c2s.bin`, смещение 20):

```
POST  HTTP/1.1\r\n                       (пути нет — два пробела)
Content-Length: <длина тела>\r\n
Accept: application/xml\r\n
Content-Type: application/xml\r\n
\r\n
```

`Host`, `Connection`, `User-Agent` нет. Тело — UTF-8 с BOM (`ef bb bf`).

## A3. Ответ и закрытие соединения

- Статусная строка успешного вызова — `HTTP/1.1 200 OK`, заголовки `Content-Length`, затем
  `Content-Type: application/xml` (`wrong-password/conn-01.s2c.bin`, смещение 5). Отказ бизнес-уровня
  (неверный пароль) — тоже `200 OK` с `crs:call_exception` в теле (`wrong-password/conn-02.s2c.bin`).
- После тела ответа — терминатор `6653b2a6` (A1), у всех ответов, включая ошибки (`probe-malformed-body`,
  `probe-unknown-method`: последние 4 байта `response.bin`).
- **Сервер соединение сам не закрывает.** У Конфигуратора первым закрывает клиент — во всех
  `wrong-password*/conn-NN.order.json` последнее событие `{"dir":"c2s","end":true}`. В пробах сервер не
  закрыл соединение ни после ответа, ни после ошибки разбора, ни без терминатора (`result.json`:
  `serverClosed: false`; пауза 1–3 с).
- Соединение переиспользуется: `probe-two-frames` — второй кадр после ответа на первый получает второй
  ответ; `response.bin` = 5 + 513 + 513, приветствие сервера одно на соединение.

## A4. Порядок рукопожатия

- Сервер говорит первым: во всех восьми соединениях Конфигуратора первое событие `order.json` —
  `{"dir":"s2c","bytes":5}` (`53f5c61a7b`), и только потом данные клиента. Прокси принимает соединение
  клиента раньше, чем сам подключается к `crserver`, так что это согласуется с тем, что клиент ждёт
  приветствие; строго (задержкой приветствия) это не проверялось.
- Ответа на приветствие клиента нет: Конфигуратор шлёт `224855b5` + 16 байт и сразу кадр, без `s2c`
  между ними (`wrong-password/conn-01.order.json`: `s2c 5`, `c2s 361`, `s2c 513`).
- Приветствие клиента серверу **не обязательно**: `probe-no-hello` — кадр `openDevDepot` без него —
  получил тот же `200 OK` и тот же `call_return`, что `probe-open` (`response.bin` по 518 байт).
  Клиенту всё равно разумно слать его, как Конфигуратор.

## A5. 16 байт после `224855b5`

- Это GUID в раскладке Microsoft (little-endian первых трёх полей): u32 LE, u16 LE, u16 LE, 8 байт
  как есть. Признак — версия и вариант UUID v4 встают на место только при такой раскладке: старший
  полубайт байта 7 всегда `4`, старшие биты байта 8 — `10`. Прямое (big-endian) прочтение дало бы
  «версии» `3` и `e` (`wrong-password`, `wrong-password-rerun`).
  Пример: `wrong-password/conn-01.c2s.bin`, байты 4–19 `8ac9d378 eb5a 3246 866d 1a50e885b42a` →
  `{78d3c98a-5aeb-4632-866d-1a50e885b42a}`.
- Внутри одного процесса `1cv8` одинаковы во всех соединениях (`wrong-password/conn-01…04.c2s.bin`,
  обе попытки аутентификации). Между процессами разные (`wrong-password-rerun/conn-01.c2s.bin` —
  `{1855871d-bc26-40e1-b324-8e31ec8f443f}`) и меняются от пересборки к пересборке фикстур.
- Сервер значение не проверяет видимым образом: пробы шлют UUID, снятый у уже завершившегося процесса
  Конфигуратора, и получают обычные ответы; без приветствия — тоже (A4). Клиенту достаточно случайного
  UUID v4 на процесс (или на подключение) в этой раскладке.

## A6. Ответы `crserver` на некорректные запросы по tcp

| Проба | Ответ (`response.bin` после 5 байт приветствия) |
|---|---|
| `probe-malformed-body` — тело «не xml» | `HTTP/1.1 400 Bad request` (строчная `r`), `Content-Length: 1334`, `Content-Type: application/xml; charset=utf-8`; тело — `exception` виртуальной ресурсной системы (`xsi:type="d1p1:Exception"`, `clsid` `c593fe3b-…`, `descr` «Ошибка разбора XML … Document is empty», `data` — base64 скобочного текста со стеком `xml2`/`crcore`/`crserver`); терминатор; соединение открыто |
| `probe-unknown-method` — `DevDepot_noSuchMethod` | `HTTP/1.1 200 OK`, `Content-Length: 3`, тело — один BOM, ни `call_return`, ни `call_exception`; терминатор |
| `probe-no-terminator` | ничего (см. A1) |
| `probe-no-hello` | обычный ответ (см. A4) |

Это то же, что по http ([07-crs-http.md](07-crs-http.md)): 400 и тело `exception` у ошибки разбора,
пустое тело у неизвестного метода. Значит, статус и тело `exception` формирует сам `crserver`, а не wsap.

## Следствия для транспорта tcp (в исходном проекте — `core/crs`, в onecdev — `CrsTcpFraming`/`CrsTcpTransport`)

1. Подключиться, прочитать ровно 5 байт приветствия (с дедлайном) и сверить с `53f5c61a7b`; затем
   `224855b5` + GUID LE.
2. Кадр запроса: заголовки из A2 в том же порядке, тело, `6653b2a6`. Без терминатора сервер молчит —
   клиентский дедлайн обязателен.
3. Ответ: статусная строка + заголовки до `\r\n\r\n`, тело по `Content-Length` (с лимитом размера),
   затем проверка терминатора. Статус не 200 — ошибка транспорта с телом `exception`; 200 с телом из
   одного BOM — неизвестный метод.
4. Сервер соединение не закрывает — закрывает клиент (после последнего вызова или по дедлайну).

## Не проверено

- Ждёт ли Конфигуратор приветствие строго (эксперимент с задержкой приветствия в прокси не ставился).
- Отправка кадров без ожидания ответа (pipelining): пробы шлют второй кадр только после ответа.
- Мусор вместо приветствия клиента и неверная сигнатура `224855b5`; тайм-аут простоя соединения на
  сервере (пауза в пробах — не больше 3 с).
- Другие версии платформы.
